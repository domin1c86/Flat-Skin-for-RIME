# 键盘记忆检查报告

## 本轮结论

检查范围为中英文状态及最近中文方案，不要求恢复数字页、符号页或符号分类。尚未复现可定位到仓库代码的记忆错误，因此本轮不修改 Lua、方案补丁或皮肤切换动作，不新增未经验证的启动恢复指令。

这不等于确认手机的重新打开行为正常：本仓库没有元书 iOS 宿主或键盘扩展源码，本环境不能运行元书，不能验证跨 App、输入框类型或键盘扩展冷启动的实际恢复。

## 已确认的实现边界

| 状态 | 当前实现 | 边界 |
| --- | --- | --- |
| 最近中文方案 | Lua 保存 `last_chinese_schema`，只支持小鹤双拼、全拼、小鹤混输；英文切回时读取 | 没有保存“最后使用的语言”字段 |
| 英文词库候选 | Lua 保存 `english_candidates_enabled`，进入英文时恢复 ASCII 模式 | 这不是中文／英文布局的启动恢复开关 |
| 中英按钮 | 皮肤选择对应布局并向 RIME 发专用组合键；Lua 选择目标方案 | 目标方案缺失时 Lua 不切换，但皮肤先前的布局动作已由宿主执行，无法据此保证两者同步 |
| 方案面板 | 同时请求对应布局与指定方案 | 从宿主原生菜单换方案，不保证皮肤同步布局 |
| 再次打开键盘 | 由宿主决定初始布局和 RIME 会话；Lua 初始化只处理当前已加载方案 | Lua 不主动选择启动方案，也不能强制恢复宿主布局 |
| 写入失败 | 运行会话中的缓存仍可继续记忆 | 不能保证扩展重启或进程终止后保留 |
| 网页预览 | 浏览器保存最近中文方案及英文候选开关 | 不读写手机文件，也没有完整的“最近语言”恢复功能，不作为手机证据 |

`init` 在宿主加载支持的中文方案时，会把该方案记为最近中文。这也支持用户从原生入口选择中文方案；但若宿主冷启动自行选择默认中文，也可能覆盖之前保存的中文 ID。当前接口无法区分这两种来源，不应凭猜测移除此逻辑。若你的错误案例涉及此场景，需要结合启动前后的方案、布局和记录文件判断。

## 自动检查

- 13项 Lua 模拟测试：三种中文方案往返、英文冷启动读取、无记录／非法记录回退、普通键／松键／非专用修饰键不误触、目标方案缺失、写入失败、英文原始输入只提交一次、候选开关恢复、未选预测取消。
- 新增检查：重新载入独立 Lua 模块后同时恢复中文方案与英文候选偏好；初始化不擅自切换宿主已选方案或提交内容。
- 7项路由测试：检查支持方案 ID、布局对应关系、中英组合动作、数字／符号返回及完整的候选开关样式。
- 这些是配置与 Lua API 模型检查，不是 iOS 生命周期或原生组合动作时序验证。

复核命令：

```text
python -m unittest discover -s tests -p test_scheme_memory.py
python -m unittest discover -s tests -p test_input_routes.py
```

## 请提供的错误案例

请在不含隐私的测试框中复现，并记录：

1. 元书版本、宿主 App、输入框类型（普通文本、搜索、网址、邮箱、数字、密码等）。
2. 出错前选用的中文方案、当前中／英文布局和英文候选开关。
3. 操作是收起后展开、切换输入框、切换 App、终止宿主 App，还是键盘扩展重启。
4. 重新打开后的键面显示和真正生效的方案；说明是只换了界面，还是输入结果也变了。
5. 手机当前是否已安装四份方案补丁与配套 Lua，并重新部署；无需发送输入正文或整个用户目录。

先区分布局、方案、候选开关三种状态，再针对可复现的源码问题修复；目前不把宿主恢复异常归咎于某个未证实的原因。
